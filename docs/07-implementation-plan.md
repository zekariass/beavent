## 1. Decisions this plan is built on

| # | Decision | Consequence |
|---|---|---|
| L1 | **The payment provider is chosen per deployment: ArifPay (default) or Chapa** (`PAYMENT_PROVIDER` = `ARIFPAY` \| `CHAPA`; decided 24 Nov 2026, replacing "Chapa only"). One provider is active at a time; both adapters are built and tested. | All online methods (telebirr, CBE Birr, M-PESA, cards, bank apps …) go through the active provider. SantimPay, direct telebirr and manual bank transfer stay out. |
| L2 | **Who holds the money follows the provider.** **ArifPay: Beavent collects** (`PLATFORM_COLLECTS`): customer payments land in Beavent's ArifPay merchant account and Beavent pays each seller out (decided 24 Nov 2026; ArifPay's public documentation does not confirm per-payment splits to seller accounts, §1.2). **Chapa: Chapa splits at source** (`PROVIDER_SPLIT`): each seller is a Chapa subaccount and Chapa settles the seller's share to their bank. | ArifPay mode needs seller balances, payout runs and payout accounts (doc 04 §9–10); payouts start as a bank batch that finance executes and confirms, automated later through ArifPay's wallet-to-bank API. **Refunds in ArifPay mode are made by hand by finance** (ArifPay publishes no refund API): the system records each refund owed, queues it in the admin console, and finance marks it paid. Chapa mode keeps the refund API and the receivable/recovery rules of §3.2. **Beavent holding customer money needs legal confirmation (D3) before ArifPay mode takes real money.** |
| L3 | **Hosting is decided later.** | Everything is containerised and cloud-neutral (PostgreSQL + PostGIS, Redis, RabbitMQ, S3-compatible storage) and runs on Docker Compose until then. A hosted staging environment is needed **before Stage 3 certification** (real provider notifications need a public URL); production before Stage 9. |

Decided (2026-11-19): **cash and pay-at-venue stay available**, recorded at POS and the box office (no provider involved, so no conflict with L1). Each business can require an **online deposit** through the active provider (`scheduling` deposit settings; Stages 3–4) to cut no-shows; platform fees on cash sales become a seller receivable recovered from later Chapa payments (§3). Event tickets sold online are paid online; cash for events only at the box office (Stage 7).

Decided (2026-11-19): **sign-in is by a one-time code to a phone or email, or with Google** (plus Apple in the iOS app, which Apple requires when Google sign-in is offered). No passwords and no authenticator apps, for anyone; sensitive actions ask for a fresh code (step-up).

### 1.1 What Chapa's documentation says, and what it means for us (Chapa mode)

From [developer.chapa.co](https://developer.chapa.co/): [split payments](https://developer.chapa.co/integrations/split-payment), [webhooks](https://developer.chapa.co/integrations/webhooks), [refunds](https://developer.chapa.co/refund), [accept payments](https://developer.chapa.co/integrations/accept-payments). Re-confirm each item in Chapa's test mode (Stage 3, step 3.1).

| Chapa fact | Design consequence |
|---|---|
| `POST /v1/subaccount` with `bank_code`, `account_number`, `account_name`, `business_name`, `split_type` (`percentage`/`flat`), `split_value`; returns a subaccount id | Created when a seller's bank account is verified. Stored as `payments.provider_accounts` (owner `ORGANIZATION`, `parent_account_id` = platform Chapa account, `sub_account_reference` = Chapa id). |
| `split_value` is the **platform's** commission; the subaccount gets the rest; values can be **overridden per transaction** | We compute the exact platform fee per order with our fee engine (`billing.fee_rules`) and send it as a **flat** override on every payment. The subaccount's default split is 0 as a safety net. |
| Subaccounts settle in **ETB** | Sellers are priced and settled in ETB. |
| `POST /v1/transaction/initialize` → `checkout_url`; amount sent as a decimal string; `tx_ref` unique; `callback_url`, `return_url`; ETB and USD | The adapter converts `amount_minor` ↔ decimal exactly. `tx_ref` = our `payment_attempts.id`. USD stays off. |
| Direct charge `POST /v1/charges?type={method}` | In the mobile app, telebirr/M-PESA/CBE Birr can use a **push prompt without a browser redirect**. Web uses hosted checkout. |
| Verify transaction by `tx_ref` | Fulfil only after a server-side verify that matches status, amount, currency, `tx_ref` and mode. Also used for polling. |
| Webhooks: `charge.success`, `charge.failed/cancelled`, `charge.refunded`, `charge.reversed`, `payout.*`; `x-chapa-signature` = HMAC-SHA256 of the payload with the secret; retried every 10 min, up to 72 h | `POST /v1/hooks/chapa` verifies the signature on the raw body, stores the event in `payments.webhook_events`, then processes it idempotently. |
| Refunds `POST /v1/refund/{tx_ref}` (full or partial, our unique `reference`); `GET /v1/refund/{ref_id}/verify`; statuses `initiated → processing → refunded \| reversed`; **refunds are deducted from the platform's Chapa balance; Chapa charges are not refunded** | **The platform funds refunds even though the seller already has the money.** We need a refund float, a seller receivable in the ledger and a recovery mechanism (§3). |
| Disputes/chargebacks are taken from the platform's account; the platform must know its subaccounts | KYB is required before a seller can take online payments. Disputes become seller receivables. |
| Transfers API and balance endpoints exist | Not needed now; usable later for refund-by-payout or recovery. |
| Test mode with test cards and test mobile numbers | Certification suite runs against test mode before going live. |

### 1.2 What ArifPay's documentation says, and what it means for us (ArifPay mode, the default)

From ArifPay's official [TypeScript SDK](https://github.com/Arifpay-net/typescript-sdk), [PHP SDK](https://github.com/Arifpay-net/phpsdk) and Postman collections ([production](https://developer.arifpay.net/postman/ArifPay-Production.postman_collection.json), [sandbox](https://developer.arifpay.net/postman/ArifPay-Sandbox.postman_collection.json)), read 24 Nov 2026; the developer portal's split, webhook and lifecycle pages could not be opened. | ArifPay fact | Design consequence |
|---|---|
| Header `x-arifpay-key`; production `https://gateway.arifpay.net`, sandbox `https://gateway.arifpay.org`; create `POST /api/checkout/session` (sandbox `/api/sandbox/c2b/session`); the SDK uses `/v0/checkout/session` | Base URL and paths are configuration; the adapter is tested against a local stub (`tools/arifpay-stub`) and the sandbox. |
| Session request: `nonce` (unique; a duplicate is refused), `items[] {name, quantity, price}`, `notifyUrl`, `successUrl`, `cancelUrl`, `errorUrl`, `expireDate`, `phone`, `email`, `lang`; production fills `paymentMethods` and `beneficiaries` from the merchant account. Response `sessionId`, `paymentUrl`, `totalAmount` | `nonce` = our `payment_attempts.id`, so a retried create can never open a second session; before retrying, the adapter looks the session up by nonce (`GET /api/checkout/getSessionByNonce/{nonce}`). One item per order with the exact total. |
| Amounts are **decimal birr** (ETB only); a default maximum of 43,200 ETB per session (third-party report) | Exact `amount_minor` ↔ decimal conversion; the route's `max_amount_minor` carries the limit. |

| `notifyUrl` webhooks are **not documented as signed** and reportedly **not retried**; one may arrive before the session updates | `POST /v1/hooks/arifpay` treats the body only as a hint: it is stored in `payments.webhook_events`, then the session is looked up with our key. Polling (doc 04 §6.2) is the main path, not a fallback. |
| **No refund or reversal endpoint** in either collection | Capability `can_refund_api = false`; refunds are recorded and paid by hand by finance (L2). |
| Direct payment routes per rail (telebirr USSD, M-PESA, CBE, Awash …) with a phone number; payouts (B2C) and wallet-to-bank need production access with an allow-listed IP | Web and app start with hosted checkout (`REDIRECT`); push prompts in the app and automated payouts come after certification. |

## 3. Money rules

### 3.1 ArifPay mode: Beavent collects (`PLATFORM_COLLECTS`)

**Flow.** Customer pays ArifPay → Beavent's ArifPay merchant account. The seller's share becomes a seller balance in the ledger (`SELLER_PENDING`, released to `SELLER_AVAILABLE` after the visit plus a delay); platform fees are netted; payouts move `SELLER_AVAILABLE` to the seller's verified bank account. Postings follow [doc 04 §10, `PLATFORM_COLLECTS`](04-payments-and-money.md#10-ledger-postings).

**Refunds.** Recorded with method `MANUAL_BANK_TRANSFER` (or `CASH` at the counter): `REFUND_INITIATED` reserves the money from the seller balance, the refund appears in the admin console's finance queue with the customer's wallet or bank details, finance pays it outside Beavent and marks it paid (step-up code, audited), which settles it. A refund after the seller was paid drives `SELLER_AVAILABLE` negative and is recovered from the next payout.

**Payouts.** Eligibility, schedules, approvals and cooling-off per doc 04 §9. Execution starts as a payout batch in the admin console (bank file and list) that finance pays and confirms; ArifPay's wallet-to-bank API replaces the manual step once production access is granted.

### 3.2 Chapa mode: Chapa splits at source (`PROVIDER_SPLIT`)

**Flow.** Customer pays Chapa → Chapa splits: **seller share → seller's bank account**, **platform share → platform's Chapa balance**. The platform share = buyer fees + seller-paid platform fees (+ VAT on fees) for that order, sent as a flat per-transaction split.

**Ledger postings**

| Event | Postings |
|---|---|
| Payment succeeded | Dr `PROVIDER_CLEARING` (platform Chapa balance) platform share / Cr `PLATFORM_FEE_REVENUE` + `TAX_PAYABLE`. The seller share is not platform money; it is recorded in `commerce` and `billing.fee_assessments` for statements. |
| Chapa fee | Dr `PLATFORM_PROCESSING_COST` / Cr `PROVIDER_CLEARING` (or charged to the customer, per Chapa terms) |
| Refund (seller share s, platform share p refunded per policy) | Dr `SELLER_RECEIVABLE` s, Dr `PLATFORM_FEE_REVENUE`/`TAX_PAYABLE` p / Cr `REFUNDS_PAYABLE` s+p → on `refunded`: Dr `REFUNDS_PAYABLE` / Cr `PROVIDER_CLEARING` |
| Recovery from seller | Dr `PROVIDER_CLEARING` / Cr `SELLER_RECEIVABLE` |
| Platform fee on a cash sale | Dr `SELLER_RECEIVABLE` / Cr `PLATFORM_FEE_REVENUE` + `TAX_PAYABLE` |

**Refund funding and recovery**
1. **Float.** Keep a refund float in the platform's Chapa balance, with an alert when it is low.
2. **Recovery** (`payments.org_settings.recovery_mode`):
   - `SPLIT_TOP_UP` (default): the seller's next transactions carry an extra recovery amount in the split, capped per transaction (`recovery_cap_bps`), until the receivable is cleared.
   - `INVOICE`: a platform invoice the seller pays through a Chapa link.
3. **Exposure limits** (`trust.risk_profiles`): a per-seller cap on outstanding receivables. Above it, refunds need seller pre-funding or admin approval.
4. **Events.** With split settlement, organizers get ticket money before the event. Controls:
   - New organizers are reviewed before publishing (`PENDING_REVIEW`).
   - Per-organizer caps on tickets sold before their first event completes.
   - Bulk-cancellation refunds above the float require organizer pre-funding.
5. Chargebacks/disputes follow the same receivable path.

Confirm these rules with the active provider and counsel before the pilot (dependencies D2, D3).

**3.2 Orders, tax and fees.** ✅ *Done* (25 Nov 2026), backend only.
- Done: a **`commerce` module** (`Orders`: `quote` and `place`) and a **`billing` module** (`Fees`, the pure `FeeEngine`). Pricing is pure arithmetic in integer minor units, half-up rounding once per line (`MoneyMath`): **promotions** on the gross line prices, then **tax** per line on what is left, then the platform's **fees** per line on what the buyer pays for it. A quote and the order placed from it use the same code.
  - **Tax** (`TaxEngine`): the seller's regime picks the rate (VAT-registered sellers VAT, turnover-tax sellers TOT; presumptive and exempt none) by the item's tax category and the day of the sale, in the market's inclusive or exclusive convention (Ethiopia: inclusive, so the price is all-in, DD6). Placing writes an immutable `order_line_taxes` row with the rate used. The seeded rates stay unverified until D7.
  - **Promotions** (`PromotionEngine`): percent off, amount off (shared exactly across the targeted lines, largest remainder), fixed price and free item; targets by service or category and by location; minimum order, maximum discount, off-peak windows (`time_windows`, in the location's time), automatic offers and typed codes, eligibility everyone / new / returning clients, per-client and total limits. Fees, tips and donations are never discounted. The best offer applies alone unless offers are stackable; a typed code that does not apply is named (`UNKNOWN`, `EXPIRED`, `USED_UP`, `NOT_ELIGIBLE`, `NOT_APPLICABLE`) and never changes the price. Platform-funded and shared offers record `platform_funded_minor`. Uses are counted when the order is placed, last, in the order's transaction (the platform's own offers through the system role, as tenants may only read them); two buyers racing for the last use: one wins, the other's order, number and counts roll back.
  - **Fees** (`FeeEngine`): `billing.fee_rules` for booking, ticket service and payment-processing fees: percentage plus fixed, then minimum and maximum, plus the platform's VAT on the fee; an organization's own rule beats the market default. **Buyer-paid fees become `BUYER_FEE` order lines** (platform VAT inside, tax category `PLATFORM_FEE`) so the price shown is all-in; seller-paid fees are recorded for payout netting (ArifPay mode) or the split (Chapa mode). Every fee is a `billing.fee_assessments` row pointing at the line it was charged on.
  - **Orders**: header, lines (service, add-on, fee), tax snapshots, redemptions, a status-history row and fee assessments in one transaction under the database's own arithmetic checks (line totals, header totals); **gapless order numbers per legal entity** (`commerce.next_document_number`, rolled back with a failed order).
- Tests: property tests of rounding and splitting (5,000 random cases each: parts add up, half-up, no part over its weight), tax (10,000 cases: inclusive and exclusive lines satisfy the line rule), fee caps and monotonicity (10,000), promotions (5,000 random baskets: never below zero, never above a line's price, fees never discounted) and whole orders (5,000: every line and header satisfies the database's arithmetic); API tests against PostGIS (placing with the tax snapshot and its immutability, VAT and TOT sellers, numbering per legal entity, buyer fee lines and seller assessments, rule precedence, codes and their limits, time windows, the last-use race, refusals).

**3.3 Deposits and prepayment at booking.** ✅ *Done* (25 Nov 2026) in ArifPay mode, on web and in the consumer app; collection in Chapa mode waits for 3.4 (it needs the seller's subaccount, so starting a payment answers `PAYMENT_UNAVAILABLE` there).

- **The payment state machine** (`PaymentProcessor`, the only place a payment is marked paid): every transition starts from a server-side lookup with our key whose reference, amount and currency match our records; a redirect or an (unsigned) notification only says where to look. Transitions only move forward. The worker (`PaymentWorker`, every 2 s) turns stored notifications into lookups and polls open attempts on the schedule 5, 10, 15, 30, 60 s, so a missing notification (ArifPay does not retry) or an early one costs seconds. **Outcomes:** paid → attempt, intent, schedule row and order paid totals (a database trigger) → the appointment is confirmed (request-to-book: requested) and the confirmation text goes out; declined → the person tries again; an unclear create (provider unreachable) is resolved by looking the session up by our nonce; a wrong amount or reference is never acted on (the attempt waits for a person); **late payment** (after the booking expired or was cancelled) confirms it again if the time is still free (the database's exclusion constraint decides), otherwise a refund of the whole payment is recorded (`APPROVED`, to be paid by hand by finance, 3.6); **duplicate payment** (a second approval for the same intent) is recorded as `SUCCEEDED_DUPLICATE` with a `REQUESTED` refund (never counted as captured).
- **Unpaid and cancelled:** a sweep expires bookings whose payment window ended (the time goes back to the calendar, the order and intents close, the provider session is cancelled where it allows, no message is sent); the customer can cancel an unpaid booking at no cost, which closes its order and payment; waitlist offers that need a deposit land on the appointment page, which has the **Pay** button.
- **Screens:** the review step (what is paid now and what is left; **Pay deposit and book**); the **payment page** (checking, booked, declined, cancelled, still waiting, released; every state from Beavent's answer); the booking page (banner and **Pay Br 360** under it, deposit lines); in the consumer app the provider's page opens outside the app and the booking screen waits and checks every 4 s; the console calendar (unpaid bookings tinted with "Payment needed", the panel says "Deposit paid Br 360. Br 1,440 to pay at the venue." or "Waiting for the deposit… held until 10:15") and the business app's visit screen. Both languages, both themes, phone and desktop were checked on screenshots.
- **Tests:** deposit rules (unit and 5,000 random prices); 11 API tests against PostGIS and an in-process ArifPay (review terms, paid on the provider's word only, return without a notification, polling, decline and retry, duplicate, expiry then a late payment confirming again, a late payment for a time someone else took going back, cancelling, provider down, wrong amount); Playwright journeys on the web (pay on the provider's page and be confirmed, decline then retry, abandon and cancel) and in the consumer app, against the ArifPay stub notifying the running API; the existing suite passes with the seed's deposit now opt-in.
- **Decisions while building:** the seed salon's deposit is opt-in (it used to be ignored); the adapter leaves out a payer number that is not an Ethiopian mobile (ArifPay refuses it, and it is optional); an unpaid appointment reserves its time as `CONFIRMED` (the schema allows `HELD` only for holds) and the sweep releases it; the payment schedule is written in the booking's own transaction, the provider is called outside any transaction.
- **Left for later:** refunding a paid deposit when the customer cancels in time, forfeiting it on a no-show, and paying the refunds (3.6); ledger postings and seller balances (3.5; the order's paid total is already kept); the seller-readiness gate on taking online payments (3.4: until then any business can set a deposit, which is safe only in the sandbox); a promo code field on the review step (pricing supports it); the front desk cancelling an unpaid booking by hand (it expires by itself); returning to the app by link after paying (the provider's return page is on the web); everything against ArifPay's real sandbox (no keys here, D1), including its notification fields and status values.

**3.4 Seller "Get paid".** ✅ *Done* (25 Nov 2026), web console and admin console; the seller's KYB document upload is not built yet (see below).

Until then deposits are not asked for: the venue page and the booking review show pay-at-the-venue, `confirm` books without a payment, and `POST …/payment` answers `503 PAYMENT_UNAVAILABLE`. `beavent.payments.require-seller-readiness` (env `PAYMENT_REQUIRE_SELLER_READINESS`, default true) switches the gate off for local development only; the local profile does, tests turn it on.
- **Payout accounts** (`ref.banks`, `payments.payout_accounts`): the seller picks one of 16 banks or 3 wallets (telebirr, CBE Birr, M-PESA; every row `is_verified = false` until codes and Amharic names are confirmed, doc 07 D2), types the holder's name and number. The holder must be the legal entity's registered name (case, punctuation and PLC/Ltd endings ignored), a bank number is 6 to 20 digits and a wallet a mobile number. Adding or withdrawing needs the `payouts.manage` permission **and a fresh code** (`STEP_UP`, the same as the admin console). One account waits for review at a time; the number is sealed with AES-256-GCM (`SecretBox`, key `SECRETS_KEY`) and only the masked tail (`••••6789`) is ever returned. Every add notifies the owner and the people with `payouts.manage` by text/email (a security notification), and payouts to a new account wait 72 hours (`payouts_allowed_after`).
- **Review** (admin console, `/payout-accounts`): the queue shows the account masked next to the registered name and the business's KYB status. Showing the full number needs `admin.payouts.approve`, a fresh code and a reason (audited); so does deciding. Approving makes it the default and retires the earlier one; rejecting records the reason the seller sees. Staff cannot decide an account of a business they belong to. Chapa mode: approving creates the Chapa subaccount from the account (`ChapaAdapter.createSubAccount`), and collections then carry the seller's split (the platform's fees and VAT stay with Beavent).
- **Screens:** "Get paid" in the business console (where you are: verification and account; the form behind a code; waiting, rejected with the reason, active with the cooling-off date; change and withdraw), both languages, both themes, phone and desktop checked on screenshots; the admin queue and review panel (English only, like the rest of that console).

**3.5 Ledger, seller balances and payouts (ArifPay mode).** ✅ *Done* (25 Nov 2026), web console and admin console; refund postings come with 3.6.
- **Ledger** (`ledger` module, `Ledger` and the pure `Postings`): one posting per business event, idempotent by key, in the caller's transaction; the database refuses an unbalanced transaction at commit (V1_13). Built: capture and fees (`PAYMENT_CAPTURED`, `FEES_ASSESSED`), release (`FUNDS_RELEASED`), payout (`PAYOUT_INITIATED`, `PAYOUT_SETTLED`, `PAYOUT_FAILED`, also for a payout the bank returned) and money received that goes back to the payer (a duplicate payment, or a late one for a time that is gone: `REFUNDS_PAYABLE`). Beavent collects (ArifPay): the whole payment is owed to the seller until the platform's share of the order's fees and their VAT is taken out, prorated to the payment (`PlatformShare`, the same figure Chapa's split uses); split at source (Chapa): only the platform share is posted.
- **Release** (`Payouts.releaseDue`, worker every 5 minutes, `beavent.payouts.worker-interval-ms`): a captured payment schedules the seller's net for `end of the service + payout delay` (the organization's `trust.risk_profiles.payout_delay_days`, else `beavent.payouts.default-delay-days`, 3). At that time the order's module says whether the service was delivered (`PaymentFulfilment.delivery`): a completed appointment, or a confirmed one whose time has passed, releases; one that was moved is looked at again after its new time; a cancelled, no-show or expired one is put `ON_HOLD` for the refund decision (3.6).
- **Payout run** (`Payouts.createDue`): one payout a day per seller and currency (the idempotency key), when the organization is verified, not `BLOCKED`, has a verified default payout account past its 72-hour cooling-off, the available balance reaches the minimum, and the schedule (`payments.org_settings`: daily, weekly on a weekday, monthly; weekly on Monday when nothing is set; manual never) is due in Addis Ababa time. The balance row is locked while the payout is made, and creating it posts the money from available to on-its-way, so nothing is paid twice. A payout waits for approval (`PENDING_APPROVAL`, with the reasons recorded) when it is the seller's first, at or above `beavent.payouts.approval-above-minor` (Br 50,000), to an account verified in the last 7 days, over the risk profile's single-payout limit, or the profile asks for review.
- **Finance desk** (admin console, **Payouts**): queues (to approve, to pay, in a bank batch, paid, failed or cancelled); approve or reject with a reason (rejecting gives the money back to the seller); **Download the bank batch** (a CSV with the full account numbers, spreadsheet-formula safe, behind a fresh code and audited; the payouts become `PROCESSING`); record **paid** (with the bank's reference), **failed** or **returned by the bank** (a reason; the money goes back to the seller). Needs `admin.payouts.approve` and a fresh code; staff cannot handle payouts of businesses they belong to; every step is audited. The seller is told when a payout is paid or does not go through (text and email, English and Amharic).
- **Seller's Earnings page** (console): what is waiting for the visit, ready to pay out, on its way and paid out so far; the payout schedule in words; the latest payouts with their status; the statement (sales, Beavent fees, payouts, returns; newest first, older on request). Both languages, both themes, phone and desktop checked on screenshots.
- **Tests:** posting arithmetic (the design document's worked example, and 2,000 random mixes where the provider always holds exactly what the seller is owed plus the platform's share); 12 API tests against PostGIS and the in-process ArifPay (a paid deposit in the ledger with fees, release after the visit and hold for a cancelled one, a moved visit, the first payout approved, exported and paid, a rejected, failed and returned payout, the rules that stop a payout, a duplicate payment held as money owed back, the finance desk over HTTP with its fresh codes and own-business rule, the seller's earnings and statement); a Playwright journey from a customer's deposit to a paid payout.
- **Decisions while building:** the payout delay defaults to 3 days (the schema's 7 is for the risk team to choose per organization); the first payout always waits for approval; a failed or returned payout goes back to the seller's available balance and is picked up by the next day's run; a payout run needs no seller action (manual payouts and editing the schedule come later, so nobody can choose `MANUAL` yet, and a seller set to it in the database is not paid until manual payouts exist).
- **Left for later:** refund postings and settlement (3.6, with the finance refund queue); `SELLER_RESERVE` holds (`reserve_bps`) and pre-event payouts (events, Stage 4); the platform's own provider fee (needs the provider statement, 3.9); fees on the part of an order paid at the venue and the marketplace commission on cash sales (`SELLER_FEES_RECEIVABLE`); seller-side schedule and manual payout request; ArifPay wallet-to-bank automation (needs production access, D1); invoicing sellers whose balance went negative.

**3.6 Refunds for deposits.** ✅ *Done* (25 Nov 2026), web (customer, console, admin console) and the consumer app's booking screen; refunds through Chapa's API are built but proven only by adapter tests.
- **Terms** (`PaymentFulfilment.settlement`, decided by the module that sold the order; appointments here): a booking **cancelled by the business** or **declined** gives the whole payment back; **cancelled by the customer** inside the free time (or while the business had not accepted a request) gives it back, after it keeps the late-cancellation fee (a percentage of the all-in price, at most what was paid) and refunds the rest; a **no-show** keeps the no-show fee the same way. The customer sees this before confirming a cancellation ("Your deposit of Br 360 will be refunded." / "Cancelling now keeps Br 180 of your deposit and refunds Br 180.") and, afterwards, where the refund stands (being arranged, on its way, sent, or kept under the terms). The business's cancel panel says the deposit goes back.
- **Settling** (`Refunds.settleOrder`, idempotent): driven by the booking's own events (`appointment.cancelled`, `.no_show`, `.declined`) through a queue in scheduling, with a sweep behind it for money the release job put on hold, so a lost event only delays a refund. Refund rows are created `APPROVED` (they follow terms the customer saw), one per payment, key `cancel:{intent}`; their method is the original method when the provider can refund by API, else by hand. The part the business keeps is released like any sale without waiting for a visit that did not happen (`ledger.scheduled_releases.settled`).
- **Ledger:** `REFUND_INITIATED` when the refund is made: Dr the seller's pending money (then available, which may go below zero and is recovered from the next payouts), Dr the platform's fee revenue and VAT on the refunded part (**fees are given back in proportion to what is refunded**), Cr refunds payable; `REFUND_SETTLED` when paid: Dr refunds payable, Cr the provider account. Duplicate payments and late payments for a time that is gone were already owed back (3.5); they are settled the same way. With a split at source (Chapa) the platform funds the refund and the business owes it (`SELLER_RECEIVABLE`).
- **ArifPay mode, by hand:** the admin console's **Refunds** page: queues *to pay* (with the customer's name, number, how they paid, why, the booking reference), *to approve* (duplicate payments), *being paid by the provider*, *paid*. Approving and marking paid (the transfer's reference) need `admin.payments.refund` and a fresh code and are audited; paying a refund the provider is already paying is refused. The customer gets a text when it is paid.
- **Chapa mode:** approved refunds are started through the provider's API (claimed first, called outside a transaction, reference = refund id) and followed by status polling every worker run; a failure goes to the finance queue to be paid by hand.
- **Tests:** 7 API tests against PostGIS and the in-process ArifPay (free cancel with fees given back and the customer told, late cancel keeping the fee and releasing it, the business cancelling inside the late window, no-show partial and total, a refund after the money was available, the finance queue with its codes and the duplicate approval, a missed event caught by the sweep); a Playwright journey (customer cancels, finance pays, customer sees it refunded).
- **Decisions while building:** fees are refunded with the refunded part (simple, and keeps the seller's net exact); refunds are events, not calls from the cancel code, so cancelling never waits on money; a refund the finance desk pays is `SUCCEEDED` on its say-so (statement matching comes with 3.9).
- **Left for later:** Chapa mode end to end (adapter tests only; the shared test context is ArifPay) and recovering what a split-at-source seller owes (`SPLIT_TOP_UP`, `SELLER_RECEIVABLE`); refunds started by the business for a single paid order or by customer support (`refunds.create`); refunds to store credit or gift cards (done in 3.8); `billing.fee_assessments` are not marked reversed (the ledger carries it); the consumer app's refund lines were not checked on a rendered screen (they share the web's wording).

**3.7 Payment links.** ✅ *Done* (26 Nov 2026) for appointments, by text message and email; WhatsApp and Telegram wait for their channels (Stage 5).
- **What a link is** (`PaymentLinks`, `PaymentLinkService`): a random token (32 bytes, base64url; only its SHA-256 hash is stored) that pays **one payment** of an order, nothing else, without signing in: the deposit (or full price) of an order waiting for payment, or the balance of a booking that stands. One link is live per payment (a database index); sending a new one revokes the earlier. A link is `OPEN`, `PAID` or `EXPIRED` (ran out, revoked, or the booking was cancelled, declined, missed or released meanwhile); a deposit link lasts as long as the booking is held, a balance link 7 days (`beavent.payments.balance-link-ttl`).
- **Paying** goes through the same provider flow as every other payment (`PaymentsService.start` now pays one chosen schedule row): the provider's page, then only a lookup with Beavent's key confirms it; the order's module decides what it means (a deposit confirms the booking and sends the customer's confirmation; a balance leaves a confirmed booking as it is and joins the ledger with its share of the fees and its own release). A balance paid for a booking that was cancelled meanwhile is refunded by the 3.6 rules.
- **The front desk** (console visit panel, `POST /v1/orgs/{orgId}/appointments/{id}/payment-link`): **Ask for the deposit by text** for a phone booking (a confirmed booking with no order: the policy's deposit applies whoever the customer is; the booking becomes `PENDING_PAYMENT` and its time is held until the link runs out, 24 hours or a quarter of an hour before the visit, `beavent.booking.link-window`; nothing is asked when the business sets no deposit, cannot take online payments yet, the client has neither phone nor email, or the visit is too close); **Send the payment link again** for a deposit not yet paid; **Send a link for the balance** for a confirmed booking with a balance. The address is shown too, to share by hand. The customer gets it by text message (email without a phone number), in their language, with the amount and the time it is open until.
- **The page** (`/{lang}/pay/{token}`, no sign-in, never indexed): the business, the services, the time in both calendars, the amount, **Pay Br 360**; after the provider sends the payer back it says "Checking your payment…" until Beavent's answer, then "You're booked" (a deposit), "Thank you, it's paid" (a balance), "The payment didn't go through" with Try again, or "This link is no longer open" with what to do. Both languages, both themes, phone and desktop checked on screenshots.
- **Tests:** 5 API tests (a phone booking asked for its deposit, text sent, paid through the link and confirmed; a fresh link replacing the earlier one, a link outliving neither its time nor its booking, made-up tokens; the balance of a confirmed booking collected with the fees prorated and no change to the booking; the conflicts and the desk's permission; a business that cannot take payments yet and a provider that is down); a Playwright journey (desk asks, customer pays without signing in on the stub, the booking is confirmed and the link spent).
- **Decisions while building:** the token travels through the outbox to the message (it only ever pays that one payment); the service names on the page are as booked (the business's language), not translated per viewer; a desk booking gets its order only when a deposit is asked for.
- **Left for later:** links for the balance of a phone booking that never had an order (it is paid at the venue), links for event tickets and invoices (Stage 4 and billing), WhatsApp and Telegram delivery, a link the customer can ask to be re-sent, and showing a link's progress (opened, paid) on the visit panel.

**3.8 Gift cards and customer balance.** ✅ *Done* (26 Nov 2026) for bookings, on the web and the API; the apps and the desk do not take cards yet (see below).
- **Selling** (`retention` module, `GiftCards`, `GiftCardService`): a business sets up **what it sells** (`catalog.manage`): a name, amounts offered as buttons, the smallest and largest amount, how many months a card lasts, and whether it sells online (`PUT /v1/orgs/{orgId}/gift-cards/program`). The venue page then links to **Buy a gift card** (`/{lang}/b/{business}/{location}/gift-cards`): amount, who it is for (given name, phone), a message, a day to send it, sign-in inline at the end (DD10), then the payment page. The purchase is an ordinary order (one line, tax category `VOUCHER_MULTI_PURPOSE`, no VAT at sale) paid in full through the provider and a payment link, so it uses every rule of 3.3–3.7. It is **the business's money when the card is sold** (same ledger path as any sale with nothing to deliver: pending, then released after the business's payout delay, a few days); the card is a liability the business carries.
- **Delivery** (`GiftCardWorker`, every minute; `beavent.retention.worker-interval-ms`): a paid card is made at delivery time (now, or the day chosen, 09:00 Addis Ababa). The code (16 letters and digits without look-alikes, four groups of four) exists in plain only in the event that sends the text message (`gift_card.delivered`) to the recipient's phone (the buyer's own, when no phone was given); **only its SHA-256 is stored**, with the last four characters for the business's list. The message says who it is from, the amount, how long it is valid, the message, and where to use it, in the recipient's language. An unpaid card is closed when its order times out; the business can **cancel** a card that is active or waiting to be sent (`refunds.create`, a reason, audited); a card past its end is written off by the worker.
- **Using a card** (`PaymentFulfilment`/`StoredValue`, `PaymentsService.tender`): on a booking's payment page, in the payment link, or through `POST /v1/me/appointments/{id}/payment/tender` and `POST /v1/public/payment-links/{token}/tender`, the person enters the code (any case, dashes optional). An unknown, spent, expired, cancelled or another business's code all answer the same `NOT_FOUND`. The card pays what it can of the deposit; **what is left is paid through the provider** as before (the schedule row is split; the booking is confirmed only when all of it is paid). A tender is an `INTERNAL` payment attempt (`GIFT_CARD`/`STORE_CREDIT`), refused while a provider payment is in progress or for an order that is itself a gift card. If the booking expires or is cancelled before it is confirmed, the card gets its money back (a refund of the tender, `SUCCEEDED` at once).
- **The money**: the business was paid when the card was sold, so a tender moves no money; it only **charges the business the fee and VAT on the part the card paid** (`FEES_ASSESSED`, taken from `SELLER_AVAILABLE`, which can go negative until the next payout nets it) and gives them back with a refund. Provider-paid parts are posted as before; the trial balance stays zero.
- **Customer balance** (`retention.customer_balances`, per customer and business): a customer cancelling a booking whose refund is owed can choose **Keep it as credit with {business}** (`refundTo: BALANCE` on cancel, kept on the appointment). The refund is then a `STORE_CREDIT` row, `SUCCEEDED` at once; the platform's fees on it are returned, the business keeps the money and owes the credit; the customer gets a text message and the booking page says "kept as credit". On the next booking's payment page the credit shows as **Use your credit with this business: Br 360** (`balanceMinor` on the payment status), spent exactly like a card.
- **Tests:** 10 API tests (setting up and the public offer, permissions; a buyer pays and the recipient gets the code by text and the console list never shows it; a card sent on a later day; a card covering a whole deposit with the fees charged and the ledger at zero; a part-covered deposit finished through the provider; refusals; expiry giving the card its money back; credit from a cancellation spent on the next booking and not by anyone else; writing off and cancelling cards; closing an unpaid card and amounts outside the limits); a Playwright journey (venue link, buy and pay on the stub, text with the code, the friend pays a deposit with it, the business's list shows what is left). Visual checks of every screen below, both languages, both themes, phone and desktop.
- **Decisions while building:** a gift card is a payment method, not a discount (the order's total does not change; fees follow what the card paid); the card's money is the business's from the sale, as in doc 04 §10, so a business cannot be paid twice and the platform keeps no stored-value liability of its own; a code never travels except in the message; cards are for the business that sold them (and its locations); the credit from a refund is per business for the same reason; credit and cards cannot pay for another gift card; the amount buttons reuse the look of the booking flow's time buttons (selected: emerald outline on `primary-subtle`), recorded as a gap in the design docs (no documented "choice chip" for the web yet).
- **Left for later:** the apps (consumer buy and redeem, the business app's cards list), redeeming at the front desk and on a point-of-sale sale (3.7's "desk" path for the balance, Stage 6), refunds of a sold card (the business cancels it and settles by hand), a manual credit adjustment by the business, credit for businesses collecting in Chapa mode (split at source: the refund stays with the provider), merging clients who hold cards or credit (they are not merged yet), service names on the pay page in the viewer's language, and expiry reminders.

**3.9 Reconciliation and go-live certification.** ✅ *Built* (26 Nov 2026) against the ArifPay stub; running it against ArifPay's real sandbox and certifying live wait for the provider terms (D1, D2).
- **Upload, not API** (`Reconciliation`, `ReconciliationService`, `admin.reconciliation`, console **Reconciliation**): finance uploads a statement for some days of one provider account (CSV: header row with `reference`, `type`, `amount`, `date`, optional `fee`; types `COLLECTION`, `REFUND`, `PAYOUT`, `FEE`, `SETTLEMENT`, `REVERSAL`, `CHARGEBACK`, `ADJUSTMENT`; major units; comma or semicolon). One statement per account and period (overlaps refused, at most 93 days, 5,000 lines); a file that cannot be read is refused naming the line. ArifPay's real export format is not known yet (D2): its columns map onto this one when it is.
- **Matching** is by the reference the provider echoes (our attempt's id, or the provider's own reference for it) **and** the amount, never the amount alone. `COLLECTION` → our payment: `MATCHED`; a different amount, or a payment we recorded as failed, is `AMOUNT_MISMATCH`; no such payment is `MISSING_INTERNALLY` and the money is posted to `SUSPENSE` (Dr clearing / Cr suspense); a payment already on a statement is `UNMATCHED`. A payment still open on our side that the provider took goes through the same late-payment path as a notification (the booking is confirmed or refunded by the usual rules); one left `UNKNOWN` that its day's statement does not show is failed. `REFUND` and `PAYOUT` lines match our refunds and payouts the same way; `FEE` lines and the fee on a collection post **`PROVIDER_FEE`** (Dr `PLATFORM_PROCESSING_COST` / Cr provider clearing, once per line) and fill `provider_fee_minor`; `SETTLEMENT` is informational; anything else waits for finance.
- **The queue** lists lines that do not match, payments we confirmed on a statement's days that the statement does not show (`MISSING_ON_STATEMENT`), and a closing balance that differs from the ledger's clearing balance at the end of the period (`BALANCE_DIFFERENCE`). Finance explains each with a note kept with their name (audited); a statement is `RECONCILED` when nothing is left and the balance agrees. Nothing is corrected silently.
- **Go-live** (console **Provider**, `GET /v1/admin/payment-provider`): checks that ways of paying exist, a payment was confirmed by lookup, a refund and a payout were paid, a statement reconciled with payments matched, and nothing is left to explain. When all pass, finance (with a fresh code) records what the live low-value payment, refund and payout were; the capabilities become `LIVE` with `verified_at`, audited. **Suspend** stops new online payments through the provider at once (its routes are switched off). The deployment must also run against the provider's live account (`PAYMENT_ENVIRONMENT=LIVE`).
- **Tests:** 6 API tests (a statement that agrees, with fees on the ledger and once per period; exceptions of every kind, suspense, explaining them; a late payment found on the statement and an unseen one failed; the ledger balance against the closing balance; file problems named by line and other separators; the go-live checks, refusal while one fails, step-up, suspend and its routes); a Playwright journey (the statement is made from the ArifPay stub's own record, uploaded in the console, matches; a second with an unexplained payment is explained). Visual checks of the console pages (the admin console is desktop-only by design).
- **Decisions while building:** upload first, because ArifPay has no known statement API; suspense is a holding place, not a resolution (explaining a line does not move the money, a ledger adjustment by finance is for later); the closing balance is optional because ArifPay mode pays refunds and payouts from the bank, so what the provider holds and what the ledger calls clearing agree only when finance enters the balance that includes those.
- **Left for later:** ArifPay's statement format and, if offered, an API or scheduled import (D1/D2); a daily reminder when no statement was uploaded; matching lines by amount, time and payer number for rails without references; chargebacks and disputes (`REVERSAL`, `CHARGEBACK` stay as lines for finance); Chapa mode end to end (adapter tests only) and its split settlement lines; a finance action that moves suspense to the right account once explained; the real-sandbox day of traffic and the live low-value test; a phone layout for the admin console.

*Done when:* a full day of sandbox traffic reconciles with zero unexplained lines (shown with the stub; the real sandbox day is the certification step above).

**Checkpoint B:** a customer books with a telebirr deposit through ArifPay; the seller's balance shows it, it is released after the visit and paid out in a batch; a cancellation in the free window lands in the finance refund queue and is paid; reconciliation matches. The same journey passes in Chapa mode with the split.

**4.1 The cash drawer and checking a visit out in cash.** ✅ *Done* (26 Nov 2026) on the API and the business console.
- **The drawer** (`commerce/CashDrawers`, `/v1/orgs/{orgId}/cash-drawer`; `pos.cash_drawer`, and `pos.sell` to look): one drawer per location, made on first use, one open session at a time (the database holds the line). It is opened with a **float**; **cash sales**, **cash put in**, **paid out** (an expense) and **taken to the safe** are append-only movements; nothing can be taken out that the drawer should not hold. It is closed with a **count**: the answer holds what was expected (float and every movement), what was counted and the variance, and the history lists closed sessions with their variance. Console page *Cash drawer*.
- **Checking a visit out** (`scheduling/Checkouts`, `GET|POST /v1/orgs/{orgId}/appointments/{id}/checkout`; `pos.sell`, and the visit's location): the bill shows the services as booked, what was paid online (a deposit) and what is due. The checkout, all in one transaction, adds **tips** (one `TIP` line per person on the order, no tax, no platform fee; the console splits a chosen percentage evenly between the people who worked on the visit and lets each amount be changed), takes the **cash** into the open drawer (the cash handed over, the change given back; only what stays is a drawer movement), **completes the visit** (the same status path as the calendar's *Complete*, so the payout release and the client's last visit follow), completes the order and issues the **receipt**. A visit with no order (a phone or walk-in booking, or pay at the venue) gets its order now (channel `PARTNER_POS`, the services as booked, fees assessed as for any order); a visit whose deposit was paid online adds the tips to its order and collects the balance only. A visit waiting for its deposit, cancelled, or checked out already is refused.
- **Receipts** (`commerce/Receipts`): the next number of the legal entity's `RECEIPT` sequence (`R0000001` …), taken in the transaction that issues it, so a rolled-back checkout leaves no gap; one receipt per order. Printing and sending it are 4.3.
- **Cash is not in the ledger yet:** the order and the payment (a `CASH` attempt tied to the drawer session) are recorded and the seller's balances do not move; the platform's fees on a cash sale are slice 4.4, which makes them a receivable from the seller.
- **Tests:** 4 API tests (the drawer's life and who may do what; a visit with no order checked out with tips, change, a receipt, the drawer and no change to the ledger, and gapless numbering; a visit with an online deposit paying only the balance and leaving the online money as it was; refusals and permissions); a Playwright journey (open the drawer, check out a visit with a deposit with a 10 % tip, short cash refused, change shown, receipt, the drawer closes level); visual checks of the drawer and the checkout in both languages, both themes, phone and desktop.
- **Decisions while building:** the checkout is one request, not a cart, so a sale cannot exist without its drawer movement or receipt; only the full amount due can be paid in cash for now (split tender is 4.2); a tip goes on the order as lines for the people it is for, so it can be paid out to them later (team pay, Stage 5) and refunded with the order; the receipt letter prefix is `R`.
- **Left for later:** discounts and promo codes at the counter (4.2), the other ways to pay and split tender (4.2), refunds of cash sales and drawer corrections (Stage 5), the drawer for box-office sessions (Stage 7), reconciling the drawer against the safe, a different drawer per till, and the business app (4.6).

**4.2 Gift cards, customer credit, split tender and discounts at the counter.** ✅ *Done* (26 Nov 2026) on the API and the business console.
- **Split tender** (`Checkouts.checkout`, `Payments.tenderAtCounter`): a checkout can name gift cards (in the order to use them), the customer's credit and the cash. Each card and the credit pay **as much as is due** (the schedule row is split, the part paid with value is its own `PAID` row, a `GIFT_CARD` or `STORE_CREDIT` attempt records it), then the cash pays the rest. A card or credit is *spent when it is taken*, so it is committed as it is taken; the cash, the visit's completion and the receipt are one transaction. If something fails midway (a code that does not work, cash that falls short) the answer says so, **the tip and what was paid are kept**, the bill lists what was paid at the counter and the sale can be finished, with other cards or cash. A request that can only fail on the cash (no cards or credit, the drawer closed, not enough cash, a bad tip, an unknown team member) is refused before anything is changed. A card that covers it all needs no cash and no open drawer. The customer's credit with the business is shown on the bill and used with a tick box.
- **Discounts** (`pos.discount`: managers and owners; `Orders.Basket.manualDiscountMinor`): a percentage or an amount, **with a reason**, on a visit that **has no order yet**: it is shared between the services in proportion to what is left of their price, tax and the platform's fees are computed on the discounted price, the reason is kept on the order (`attribution`), and it is never more than the visit costs (a visit can be given away). A visit whose deposit was paid online keeps the prices it was sold at (its tax snapshots are immutable) and is refused a discount.
- **A payment link for the balance** (a visit whose deposit was paid online): the checkout has **Ask the customer to pay by text**, which uses the 3.7 link for the balance; the page then looks every few seconds, and when the balance is paid only the tip (if any) and the completion are left. For a visit with no order the link would be a deposit, so it is not offered there.
- **Tips** go on the order once: a sale that was started keeps the tips it has (the tip a person was shown is the tip they pay); tip percentages are taken on what is due after the discount.
- **The ledger**: still nothing for cash, gift cards or credit at the counter; the fees on everything paid at the venue are slice 4.4 (the business was paid for a gift card when it was sold, so redeeming it moves no money).
- **Tests:** 3 more API tests (a card and cash sharing a sale with the change, and a card covering it with the drawer closed; the customer's credit spent, a failed card keeping the tip, a short cash after a card leaving the sale to finish; discounts: who may give them, validations, percent and amount, never more than the visit costs, refused on a deposit visit); a Playwright journey (a discount for a reason, a gift card and cash together, the change and how it was paid); visual checks of the filled-in form, a failed card, a started sale and the finished receipt in both languages, both themes, phone and desktop.
- **Left for later:** a QR code for the payment link and a provider prompt to the customer's phone at the counter (a QR library needs approval first; the link by text covers the need for now), paying a visit that has no order by link, discounts and promo codes on a visit that already has an order (a re-pricing that keeps the immutable tax snapshots), a gift card sold at the counter (4.5 with products), the business app (4.6).

**4.3 Receipts.** ✅ *Done* (26 Nov 2026) for the visits checked out at the counter; email delivery waits for the email channel.
- **The receipt** (`Receipts.view`, `GET /v1/orgs/{orgId}/orders/{orderId}/receipt`; `pos.sell`): the seller's **registered name and TIN**, the location, its landmark and phone, the number and date in both calendars, the order number and customer, the lines as sold (services as they were named when booked), the discount, the tips by person, the **tax by code and rate** (included or added, from the immutable tax snapshots), the total, and **how it was paid** (the deposit paid online, gift cards, credit, cash). Numbers are the gapless `R0000001` … of the legal entity (4.1).
- **Printing:** the console page *Receipt* (`/business/o/{orgId}/receipts/{orderId}`) and the customer's page (below) are narrow, like a till receipt, with no menus when printed, and **always printed in the light theme** (the print dialog switches the page to light, so a dark screen does not print pale text on white paper). Reached from the finished checkout and from a checked-out visit.
- **Sending** (`POST …/receipt/send`): the customer gets a text message in their language (email without a phone number: the email channel is Stage 5, so only the text message arrives for now) with the business, the number, the total and a **link** `/{lang}/receipt/{token}`. The link opens the same printable page **without signing in** (`GET /v1/public/receipts/{token}`, never indexed); only its SHA-256 is kept; **sending again makes a new link and ends the old one**; the receipt records how it was delivered. A customer with neither a phone number nor an email is refused clearly.
- **Tests:** 1 more API test (the receipt with its lines, tenders adding up to the total, permissions and another business's order; sent by text, the link opening it, wrong and short links refused, only a hash kept, a second send ending the first link, a customer with no contact); the checkout journey now opens the receipt, sends it and opens the link as the customer; visual checks of both pages in both languages, both themes, phone and desktop, with a discount, an invalid link, a customer with no contact, and the print layout.
- **Decisions while building:** the receipt is built from the order, not copied when issued, so it cannot disagree with it (a later correction is a credit note, Stage 5); service names are the business's own, as booked; the tender list is what the payment attempts say, so a part payment by link shows as it was paid.
- **Left for later:** email delivery, WhatsApp and Telegram, sending to another number than the client's, a fiscal receipt number from the tax authority (`fiscal.documents`, Stage 8), a thermal-printer or PDF export, the cash tendered and the change on the receipt (they are not kept), and a receipt for a sale with no customer.

**4.4 Platform fees on sales paid at the venue.** ✅ *Done* (26 Nov 2026) for counter checkouts; the marketplace new-client commission is not charged yet (below).
- **A receivable from the seller** (`Payouts.chargeVenueFees`, `Postings.venueFees`): when a visit is checked out, the platform's fees on the part **paid at the venue** (cash, gift cards, credit) are charged to the business as `Dr SELLER_FEES_RECEIVABLE / Cr PLATFORM_FEE_REVENUE + TAX_PAYABLE` (`FEES_ASSESSED`, docs/04 §10): the fees assessed on the order, with VAT, **less what its online payments already took** (read from the ledger), so a visit paid partly online and partly at the counter pays its fees exactly once, whatever the split. **Tips carry no fee**, and a sale with nothing paid at the venue for the sale itself charges nothing. Once per order (idempotent key `venuefees:{orderId}`).
- **Taken from the next payout** (`PayoutService.createFor`): when a payout is created, what the seller owes is netted off it first (`FEE_COLLECTED`: `Dr SELLER_AVAILABLE / Cr SELLER_FEES_RECEIVABLE`), in the same transaction; a payout that is all fees makes no payout and the fees are settled. A seller with only venue sales and no online money keeps the receivable until an online sale is released; **invoicing** a seller who never has a payout to net it against is for later (billing).
- **Safety net:** the charge is made after the checkout commits; if it fails, the payout worker's sweep (`sweepVenueFees`, every run) charges completed orders that have venue payments and fee assessments but no charge yet.
- **The seller sees it:** *Earnings* shows **Fees to be taken from your next payout** (`feesOwedMinor`), and the statement shows the amount taken from a payout.
- **Tests:** 2 API tests (a cash sale and a sale paid with a gift card each owing 5,750, the tip carrying none, nothing charged twice by a second call or the sweep, no money moved, the ledger balanced; a visit with an online deposit owing 4,600 of the 5,750 and the payout of 8,850 becoming 4,250 with the fees settled); the checkout journey checks the earnings page; visual checks of the earnings page in both languages.
- **Decisions while building:** the fee is charged at checkout, not at each tender, because a sale that is abandoned midway has not been sold; the share is "what is left to charge", not a proportion, so rounding in the online payments cannot leave a coin owing or overcharge; the receivable is the seller's debt and nobody else's: refunds of counter sales (Stage 5) will give it back the same way the online fees are given back.
- **Left for later:** the **marketplace new-client commission** (docs/04 §11): it needs the marketplace source of the client and a fee rule for it, which belong to the marketplace stage, and will use this same receivable path (a `MARKETPLACE_NEW_CLIENT` assessment at the first completed visit); a visit completed with the calendar's *Complete* button instead of the counter (nothing is paid at the venue through the platform, so nothing is charged); invoicing sellers who have no payouts to net against; giving fees back when a counter sale is refunded (Stage 5); the sweep is not covered by a failing-charge test.

**4.5 Products.** ✅ *Done* (26 Nov 2026) for the console; the business app is 4.6.
- **Catalogue** (`catalog.products` / `product_variants`, `Products`, `GET/POST /v1/orgs/{orgId}/products`, `PUT .../{productId}`): a product has a name in each language, a brand, a tax category, whether its stock is counted, and one or more variants (a label such as "250 ml", SKU, price, cost). A product is saved whole; archiving hides it from the counter but keeps old orders readable. The list needs `pos.sell`, `catalog.manage` or `inventory.manage`; changes need `catalog.manage`; **cost and archived products** are shown only to those who manage the catalogue or stock.
- **Stock** (new module `stock`, `Stock`): every change is an immutable `stock.movements` row (`RECEIPT`, `SALE`, `RESTORE`, `ADJUSTMENT`, `DAMAGE`) and the level (`stock.levels`) is kept by a trigger (`apply_movement`, `SECURITY DEFINER` so the app role cannot edit levels directly); a level cannot go below zero. `POST /stock/receipts` (stock arrived), `POST /stock/adjustments` (a correction, or lost or damaged), `GET /stock/movements`; all need `inventory.manage`.
- **Selling goods:** an order line can be a `PRODUCT` (`LineInput.productVariantId`, `Orders.addProducts`), priced, taxed (the product's tax category, snapshots kept) and totalled like any other line. At a **visit's checkout** goods are added once to the visit's order (with or without an online deposit) and paid with the rest; a **discount applies to the services** of a visit, or to the goods in a goods-only sale; tips are on services only.
- **Walk-in sales** (`Sales`, `POST /v1/orgs/{orgId}/sales`, `GET .../{orderId}`, `.../payment`, `.../cancel`): an order with no visit. *Start* makes the order (confirmed, to be paid at the venue) and takes the goods off the stock; *pay* uses the same split tender as a checkout (`Tendering.collect`: gift cards, credit, cash, change, receipt); an unpaid sale can be *cancelled* and the goods go back on the shelf. Two steps, so a retry never makes a second order or takes the stock twice.
- **Console:** *Products* (list with stock at a location, add, change a price, stock arrived, correct or write off, archive), *Sell* (steppers, then the payment screen with gift cards, credit, cash, change, cancel and the receipt), and a **Products** section in the visit's checkout.
- **Tests:** 5 API tests (catalogue, permissions and archiving; movements and the floor at zero; a walk-in sale paid in cash with change, receipt, stock and an untouched ledger; cancelling restores stock, a gift card plus a discount; goods on a visit's order, with and without an online deposit, stock checked); a browser journey (add a product, receive stock, sell two in cash, sell one at a visit's checkout); visual checks of the three screens.
- **Decisions while building:** goods are added once per order like tips (a second checkout call cannot double them); the stock check is the database's `on_hand >= 0`, so two tills cannot oversell; products carry no platform fee unless a fee rule targets `PRODUCT`; the up-front cash estimate is approximate for tax-exclusive regimes.
- **Left for later:** purchasing (suppliers, purchase orders), stocktakes, transfers between locations, product photos and barcode scanning, platform fees on goods, refunds and returns of goods (Stage 5), selling gift cards at the counter, and retail in the business app (4.6).

**8.3 Reviews.** *Done for places* (26 Nov 2026).
- Verified reviews after completed visits and events; organization responses; moderation queue in the admin console.
- **Rules.** Only the person with a **completed appointment** at the place can review it (the database already required an appointment or an order), **once per visit** and within **90 days** of it. One to five stars and an optional comment of up to 1,000 characters. The person can edit or delete their own review while it is published. The author shows as given name and the initial of the father's name ("Hana T."), or "A customer" with no name; the visit shows as its day in the reader's calendar, the service in the reader's language and who did it.
- **Backend** (discovery module, migration `V8_03`: permission `reviews.respond` for owner, administrator and manager, and indexes). `Reviews` API. Public: `GET /v1/public/businesses/{slug}/reviews` (`location` narrows to a place; summary with average, count and star distribution; cursor pages). Business (`reviews.respond`): `GET /v1/orgs/{orgId}/reviews` (`unanswered`), `PUT` and `DELETE …/{id}/response`, `POST …/{id}/report` (reason and details; one open report at a time; the report goes to `trust.content_reports`). On the server set `PUSH_PROVIDER=expo` (the default) and, only if the Expo project requires it, `EXPO_PUSH_ACCESS_TOKEN`. Receipts are not polled yet (a device that went away after Expo accepted the message is found by the next send).

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Chapa split/refund behaviour differs from its docs | Payments rework | Confirm early (3.1); adapter isolates changes; test-mode suite |
| Single provider, no failover | Lost sales during a Chapa outage | Health monitoring; pay-at-venue fallback for appointments; status banner; confirmation retries; a second Ethiopian provider kept ready to enable |
| Refund float exhausted (e.g. a large event cancelled) | Delayed refunds | Float alerts, per-organizer exposure caps, pre-funding for bulk refunds, organizer review |
| Organizer takes the money and cancels | Platform absorbs refunds | KYB before online sales; caps before the first completed event; recovery via split top-up; terms making organizers liable |
| Hosting decision not made | Stage 3 can't receive real webhooks | Build against the Chapa stub; D5 is a hard prerequisite for Stage 3 certification |
| SMS cost and deliverability | OTP failures | Telegram channel; delivery monitoring; per-message cost tracking |
| Scope creep into growth features | Pilot slips | Stages 0–10 are the pilot scope; new requests go to Stage 11 unless a pilot partner is blocked |
| Availability engine complexity | Wrong slots offered | Spec first; property tests; DB exclusion constraint as the backstop |
| Public booking abuse (bots holding slots, fake bookings) | Lost sales, annoyed businesses | Short holds, per-IP and per-phone limits, a cap on live holds per person, phone verification before a booking is confirmed, business can block a customer |
| Realtime fan-out (calendar, payment status, check-in) | Stale calendars, load spikes | One platform channel with Redis fan-out, refetch-on-notify (small messages), polling fallback, load test in 9.1 |
| Amharic and Afaan Oromo copy quality | Mistrust of messages and screens | Native-speaking editor review before pilot; templates kept in `@beavent/i18n` with fallbacks |
